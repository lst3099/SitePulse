# 方案 MECE 与业务闭环待确认事项

## 一、文档目的

本清单用于核实《施工人员与设备智能管理平台方案文档》是否满足以下要求：

1. 业务场景、用户角色、业务规则、异常场景之间不重叠、不遗漏；
2. 方案回归业务本质，真正解决人员进出控制、通行记录可信和考勤可追溯问题；
3. 各业务流程均形成“触发 → 执行 → 输出 → 反馈 → 结束”的完整闭环。

请在各项“待确认”后补充结论。标记为 P0 的内容建议在软件详细设计和接口设计前确认。

## 二、当前已确认的业务基线

### 2.1 项目与设备

- 工地和项目是同一个概念，统一称为“项目”。
- 一个项目可以有多个出入口。
- 不同出入口的设备统一纳入同一个项目的考勤统计。
- 只要设备绑定到当前项目，设备产生的打卡记录就归属当前项目。
- 设备绑定关系至少包含项目、设备、出入口、进出方向、绑定状态和生效时间。
- 设备更换或解绑后，历史设备事件和历史项目归属继续保留。
- PC 端保留项目新增、编辑、查询、停用或归档功能。
- 已经产生人员、设备、考勤或工器具数据的项目不做物理删除。

### 2.2 人员与权限

- 人员主档案与项目人员关系分开保存。
- 一个人员可以同时或先后关联多个项目。
- 人员进入项目后，需要同步人员档案、人脸和门禁权限。
- 人员离场后撤销项目设备权限，但保留历史关系和历史考勤。
- 首次授权同步失败时，设备没有有效权限，人员不允许进入。
- 平台要求撤销权限但设备同步失败时，设备侧暂时保留原权限，并记录同步异常。
- 健康报告不是进入权限条件。
- 年龄超过项目阈值后次日默认禁止进入。
- 确需继续进入时，由管理员或项目负责人直接登记特殊授权及有效期；平台不提供审批流程。
- 本期不支持现场人脸采集。

### 2.3 通行与考勤

- 设备原始事件不可修改、不合并。
- 平台考勤结果允许通过人工补录重新计算。
- 本期只有补录，没有考勤修正。
- 按“项目 + 人员 + 日期”汇总所有出入口的有效记录。
- 当天任意有效进门或出门记录都算正常出勤。
- 没有任何有效进出记录才判断为缺勤。
- 最早有效进门记录用于判断迟到。
- 最晚有效出门记录用于判断早退。
- 仅有一个方向的记录仍算正常出勤，但保留异常标识。
- 加班统计暂不纳入本期。
- 节假日和请假按项目管理员登记的规则处理。

### 2.4 健康、工器具和告警

- 健康报告非必填，支持图片，10MB 以内，无需审核。
- 健康报告有效期按体检日期加一年计算。
- 健康报告仅展示有效期，不影响进入权限。
- 历史健康报告长期保存。
- 年龄阈值初始为 60 岁，提前 30 天预警，阈值支持项目配置。
- 告警接收人为系统管理员和项目负责人，方式为站内信。
- 平台所有告警统一通过站内信推送，不使用短信、邮件等其他方式。
- 不设置告警等级，不要求人工确认关闭。
- 设备恢复在线后自动关闭离线告警。
- 保存成功通行、识别失败和权限过期人员的抓拍照片。
- 不保存未登记人员抓拍照片。
- 工器具二维码和定期检查作为独立业务模块保留。
- 不提供远程开门。

### 2.5 人员档案与移动端账号

- 人员档案和平台登录账号分开管理。
- 人员管理维护人员主档案、项目关系、人脸、健康报告和资质证书。
- 用户管理维护登录账号、账号状态、角色和数据权限。
- 一个施工人员最多关联一个移动端账号；人员可以没有移动端账号，但不能因此影响其设备通行权限。
- 在人员详情中提供移动端账号开通、停用和重置入口。
- 施工人员开通账号后分配“打卡人员”角色，只能登录 APP 查看本人相关信息。
- 打卡人员可以查看本人考勤、进出记录、本人相关抓拍、个人信息和本人相关项目。
- 人员关联多个项目时，APP 通过项目范围控制数据查看范围，并支持项目切换。
- 人员离开一个项目时，移除该项目 APP 数据查看范围和设备通行权限，但保留其他项目权限。
- 人员离开全部项目时，可以停用移动端账号，但保留人员档案和历史业务数据。
- 移动端账号停用不等同于设备权限撤销，账号权限和门禁权限分别控制。

## 三、第一性原理检查

### 3.1 业务本质

本项目的本源目标不是单纯接入海康 SDK，而是解决以下问题：

1. 谁可以进入项目；
2. 设备实际发生了什么通行行为；
3. 哪些通行行为可以形成考勤；
4. 异常发生后能否发现、追溯和处理。

### 3.2 建议采用的核心状态模型

平台需要区分以下三种状态，不能合并为一个“权限状态”：

| 状态 | 含义 |
|---|---|
| 平台应有权限 | 根据项目关系、人员状态、年龄和特殊授权计算出的结果 |
| 设备已生效权限 | 最近一次成功同步到具体设备的权限结果 |
| 实际通行结果 | 设备当次识别、权限校验和开门反馈产生的结果 |

当前已确认“平台禁止但设备同步失败时，设备可能仍允许进入”，因此必须保留上述状态差异，并在记录中展示同步时间和异常状态。
不考虑这个情况，只要人脸信息同步到设备上，且开启授权，就有权限通行。

### 3.3 考勤计算本质

建议将考勤计算明确为：

```text
是否需要考勤 = 项目当天为工作日 且 人员当天未请假

需要考勤时：
  存在有效设备事件或有效补录记录 → 正常出勤
  不存在有效设备事件和补录记录 → 缺勤

最早有效进门时间 > 上班时间 + 迟到宽限时间 → 迟到
最晚有效出门时间 < 下班时间 - 早退宽限时间 → 早退
```

其中“有效设备事件”的定义仍需确认，不能只使用“收到了一条设备事件”作为判断依据。
有效设备事件：工人在项目任意设备刷脸且存在刷脸记录，即为有效事件

## 四、MECE 核查结果

### 4.1 业务场景划分

建议将业务场景划分为以下六类：

| 编号 | 业务场景 | 主要内容 | 核查结论 |
|---|---|---|---|
| A | 项目与基础配置 | 项目、出入口、人员分类、考勤规则 | 基本覆盖 |
| B | 人员授权生命周期 | 人员进场、人脸录入、同步、离场、超龄审批 | 部分覆盖 |
| C | 现场通行 | 人脸识别、门禁校验、放行或拒绝、事件产生 | 部分覆盖 |
| D | 考勤结算 | 原始事件、按日汇总、迟到早退缺勤、补录 | 部分覆盖 |
| E | 异常与恢复 | 设备离线、同步失败、权限不一致、事件补传 | 不完整 |
| F | 查询与反馈 | PC、APP、报表、告警、操作日志 | 基本覆盖 |

工器具二维码属于独立业务域，不属于人脸考勤主链路，建议保留但单独管理。同意

### 4.2 当前存在的边界重叠

#### 人员档案、项目人员关系、设备权限

建议明确为：

```text
人员档案：人员是谁
项目人员关系：人员属于哪个项目
设备权限：人员在具体设备上是否可以通行
```

三者应分别维护，不能共用一个“人员状态”。

人员档案是施工人员的信息
项目人员：从施工人员中人，派遣到某个项目
施工人员开通账号时，新建一个平台登录账号，并与人员档案建立唯一关联；如果该人员已有系统账号，则直接关联已有账号，不重复新建。
具体规则：
- 人员档案创建后，初始状态为“未开通账号”；
- 点击“开通移动端账号”时新建账号并绑定人员；
- 如果手机号或已有账号已经属于该人员，则复用原账号；
- 一个施工人员只能关联一个登录账号；
- 同一个人既可以是施工人员，也可以是项目负责人，使用同一个账号增加多个角色；
- 不允许为同一个人分别创建施工人员账号、项目负责人账号；
- 账号停用不删除人员档案，也不删除历史考勤；
- 账号登录权限、项目数据权限、设备通行权限分别管理。

#### 项目设备、设备管理、设备绑定关系

- 项目管理：维护业务上的项目出入口；
- 设备管理：维护设备主档案、在线状态和同步状态；
- 项目设备绑定：维护设备属于哪个项目、哪个出入口以及何时生效。

同一绑定关系不能由多个页面分别维护多套数据。

#### 原始事件、平台考勤结果、人工补录

- 原始设备事件：不可修改的设备事实；
- 人工补录：新增的考勤依据；
- 平台考勤结果：根据原始事件和补录重新计算的结果。

平台考勤结果不能作为下一次考勤计算的输入。

#### 告警、同步日志、操作日志

- 告警：需要管理员或项目负责人关注的业务或设备异常；
- 同步日志：平台与海康设备之间的接口交互过程；
- 操作日志：用户在平台中执行的操作。

### 4.3 当前存在的可能遗漏

- 设备登记、绑定、解绑、更换、停用、归档的完整生命周期；
- 人员加入项目、离场、重新加入项目的完整授权流程；
- 项目停用或归档后设备权限和新事件的处理；
- 实时事件与历史补传事件的去重；
- 设备更换项目后，迟到历史事件的项目归属；
- 设备时间、平台时间和考勤日期的确定方式；以设备时间为准
- 项目负责人和特殊授权登记人的角色边界；项目中不设置独立考勤负责人，由项目负责人负责考勤统计
- 补录错误后的恢复方式；可以删掉，重新统计
- 年龄预警的接收人和通知方式；站内消息推送，移动端和网页端接收
- 同步异常恢复后的自动关闭和重新授权规则。
